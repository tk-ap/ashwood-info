FOUNDATIONAL INFRASTRUCTURE / NOT A PUBLIC OFFERING

How does agent work stay governable when execution moves across tools and hosts?

Agent OS is the private control plane underneath the work: a way to resolve what should happen, who or what can do it, where it runs, what evidence is required, and where human authority remains explicit.

THE ROLE

Infrastructure, not another product.

The ecosystem does not need another public SKU called Agent OS. It needs a shared execution layer that can support several products without letting any one of them become the sovereign authority over the rest.

The through-line

ALVIRA maintains context. ailhat helps direct attention. Product-specific governance defines what is allowed. Agent OS carries a governed task through agents, skills, harnesses, hosts, branches, previews, verification, and evidence.

The host is not the authority.

A workstation, cloud harness, CI runner, or future Omarchy machine can host execution. The host should not decide what the agent is permitted to do. Authority stays in the control plane and ultimately with the human operating it.

SEP 01, 2026 / ARCHITECTURE TURN

The repository became a control plane instead of a collection of agent definitions.

The important change was conceptual first, then machine-readable.

Governed execution charter

The repository now defines the path from a work item into a governed task with explicit context, authorization, routing, execution, evidence, and acceptance boundaries.

Phase 1 contracts

Minimal contracts now exist for task, workflow, harness, host, and evidence. They are declarative on purpose: enough to give the control plane a common language without turning on autonomous execution.

Recurring work and agent identity

Recurring-work became a first-class governed capability, while agent identity design remains bounded: identities can be created and reviewed without allowing agents to proliferate themselves dynamically.

Omarchy became a host profile.

The sovereign-computer idea became clearer once Omarchy was treated as one possible execution environment rather than the governing brain. The same control contracts should survive a change of host.

REFERENCE PILOT

ASHWOOD became the first useful failure.

A real mobile UI task exercised the control-plane chain and exposed the distinction between execution and verification.

The system could execute the task.

The work could be routed, changed on a branch, deployed to a preview, and recorded with evidence.

The human could still reject the result.

Repeated previews failed for different reasons: layout, interaction grammar, visual fidelity, and the feel of motion. Those failures changed the implementation architecture and became evidence the next pass could use.

That is the point.

A governed workforce should make execution cheaper and more repeatable without making acceptance invisible. The control plane is useful when it preserves both machine leverage and the boundary of human judgment.

CURRENT STATE

The contracts exist. The runtime is intentionally still bounded.

The next work is integration: binding product repositories and local manifests into the router, proving more reference tasks, and only then deciding which execution loops deserve greater autonomy.

What I am not optimizing for

Maximum autonomy, persistent agents everywhere, or a demo that can claim it runs by itself.

What I am optimizing for

Clear authority, portable execution, reusable evidence, bounded loops, and a system that can explain why work was done—not merely that it ran.
